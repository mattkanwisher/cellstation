# SPU sync-kernel reverse-engineering — Dead or Alive 5 Ultimate

Both kernels are **SPURS kernel scheduler glue**, not compute. Both take an EA in main
memory, `GETLLAR` a **128-byte (0x80) reservation line**, mutate a bitmap/flags region
in-place, then `PUTLLC` and retry on failure. That 128-byte line is the head of the
`CellSpurs` structure — the workload-management area (`wklReadyCount / wklStatus /
wklFlag / current-contention / max-contention / running-set` bitmaps) that the SPURS
kernel CASes to pick and claim the next workload. This is precisely the reservation
traffic that shows up host-side as `writer_lock` contention in rpcs3.

---

## Kernel 9 — LS 0xfbf0 (`skvmPX76pxF`, 1.05%)

### Atomic RMW (LS 0x1007c–0x10140)

```cpp
// EA of the CellSpurs management area passed in r14:r16 (EAH:EAL); line mirrored to LS 0x80
// The 0x80-byte line = six live quadwords at LS 0x80,0x90,0xa0,0xb0,0xc0,0xd0
do {
    getllar(/*LSA=*/0x80, /*EA=*/spurs_mgmt_ea, /*size=*/0x80);   // load-locked 128B

    v128 q80 = load(0x80), q90 = load(0x90), qa0 = load(0xa0);
    v128 qb0 = load(0xb0), qc0 = load(0xc0), qd0 = load(0xd0);

    // Reduce the ready/status/contention bitmaps across the line:
    //   or/and/andc mix the per-workload masks, cntb+sumb = popcount of "ready" bits,
    //   orx = horizontal-OR to a single "any work pending?" predicate.
    u32 any_ready = orx(mix(qa0,qc0,qd0,...));          // r11
    u32 ready_cnt = sumb(cntb(andc(...)));              // r23 -> r4 (count)
    v128 new_running     = andc(or(q90..), qb0);        // r3  (claim/clear bits)
    v128 new_contention  = and(qc0, q80..);             // r6
    v128 zero            = 0;                           // r19

    if (any_ready == 0) {                               // brnz r5 skips the store
        store(0x90, new_running);      // update running / ready-count word
        store(0xc0, new_contention);   // update contention word
        store(0xa0, zero);             // clear an event/flag word
    }
} while (putllc(/*LSA=*/0x80, spurs_mgmt_ea, 0x80) != 0);   // store-conditional, retry on loss

// after commit: iterate over the (ready_cnt-1 .. 0) selected workloads
int i = ready_cnt - 1;                                 // r80 = r4 - 1
do { i += spurs_dispatch_workload(i, ...); } while (i >= 0);   // brsl 0x104a8 loop
```

### Plain English
Atomically reads the 128-byte `CellSpurs` workload-management line, computes which
workloads are ready (population count over the ready/contention bitmaps), and — when the
guard holds — writes back the updated running-set, contention, and a cleared flag word,
committing with `PUTLLC`. It then walks the selected workloads. This is the SPURS kernel's
**select-and-claim-workload** atomic followed by the dispatch loop.

### Name: `spurs_kernel_select_workload_cas`
- Shared structure: `CellSpurs` management area (ready/running/contention bitmaps), 128B line.
- Operation: lock-free scheduler decision — pick next ready workload, claim it (contention
  update), commit via store-conditional; then dispatch.
- **Confidence: high** that it is SPURS scheduler-select; medium on the exact field
  semantics of each written word (0x90/0xc0/0xa0) without the CellSpurs struct offsets.
- SPURS-sync: **confirmed** (GETLLAR/PUTLLC RMW on the SPURS control line, not compute).

## Kernel 10 — LS 0x00a78 (`VdJXQxfS4gC`, 0.92%)

Three distinct reservation critical sections on the same 128-byte SPURS line.

### (A) Workload state-flag transition (LS 0xb88–0xbf4)

```cpp
do {
    getllar(0x80, ea, 0x80);
    u8  st = read_status_byte(line);           // rotqby-extracted scalar
    u32 was_set = st & 0x08;                    // test bit 3
    u8  a = (st & ~0x08) | 0x01;                // clear 0x08, set 0x01
    u8  b =  st | 0x10;                         // set 0x10
    u8  nv = was_set ? a : b;                   // selb
    write_status_byte(line, nv);
} while (putllc(0x80, ea, 0x80) != 0);
```
A 3-state transition on a workload status/flag byte (idle→ready→running / shutdown style
bit dance). Classic SPURS `wklFlag`/`wklStatus` update.

### (B) Job dequeue with copy-out (LS 0xc84–0xd30)

```cpp
do {
    getllar(0x80, queue_ea, 0x80);             // lock queue-descriptor line
    u32 idx  = read_index(line) & 0xff;        // head/slot index (r32)
    v128 elem = load_indexed(line, idx);       // lqx the queued entry
    // copy the dequeued packet out to main memory while holding the reservation:
    put(/*plain DMA*/ elem_dst_ea, elem, 4);   // MFC PUT (not conditional)
    write_back_slot(line, idx, ...);           // advance head / mark consumed
} while (putllc(0x80, queue_ea, 0x80) == 0 ? /*done*/break : /*retry*/true);
// brz r36 -> success -> exit; else retry
```
Reads a queue descriptor, extracts the head slot, DMAs the dequeued element out, updates
the head/consumed marker, commits with `PUTLLC`. This is a **lock-free job/work-queue
dequeue**.

### (C) Management-bitmap read + reduce (LS 0xdcc / 0xe74, mirror at LS 0x2700)

```cpp
getllar(0x2700, ea, 0x80);                     // GETLLAR the management line
v128 w0=load(0x2700),w1=load(0x2710),...w7=load(0x2770);
// same or/and/andc + cntb/sumb/orx popcount idiom as kernel 9:
u32 any = orx(reduce(...));                    // is any workload ready?
u32 cnt = sumb(cntb(...));                     // how many
// -> drives priority selection (ceq against 0x42494e32/'BIN2', clz for highest bit, selb)
```
Reads the same SPURS bitmap area and reduces it to a "ready?/count/highest-priority"
decision — the read half of the scheduler-select seen in kernel 9. (The `'BIN2'` /
`0x42494e32` compare and `clz`-based highest-set-bit pick are the workload-priority scan.)

### Plain English
The SPURS **taskset / job-chain kernel**: it flips a workload's status flag, dequeues the
next job packet from a lock-free queue (copying it out under reservation), and re-reads the
management bitmap to choose the next ready workload by priority. All three sections are
GETLLAR/PUTLLC RMWs on the CellSpurs / job-queue lines.

### Name: `spurs_taskset_jobqueue_dequeue_cas`
(sub-parts: `spurs_wkl_status_flag_cas`, `spurs_jobqueue_dequeue_cas`, `spurs_kernel_ready_scan`)
- Shared structures: `CellSpurs` workload-status byte; a lock-free job/work queue
  descriptor; the SPURS ready/contention bitmap.
- Operations: status-flag transition (CAS), queue dequeue + copy-out (CAS with embedded
  PUT), ready-bitmap scan/priority select.
- **Confidence: high** that these are SPURS taskset/job-queue synchronization; medium on
  precise queue-slot field offsets.
- SPURS-sync: **confirmed** — three reservation loops, one carrying a payload DMA, all on
  SPURS control lines.

## HLE impact
Yes — both kernels are **prime targets for SPURS-kernel HLE**. rpcs3 already ships an HLE
`cellSpurs` path (`spursKernelSelectWorkload` / taskset dispatch in
`Emu/Cell/Modules/cellSpurs*.cpp`). With the SPURS kernel HLE'd, these guest GETLLAR/PUTLLC
polling loops on the 128-byte `CellSpurs` line never execute on the SPU LLE path, which
**eliminates exactly the reservation traffic causing the host-side `writer_lock`
contention**. Neither kernel is a compute kernel — there is nothing here to rebuild as
optimized C++; the win is removing the polling, not accelerating it.
